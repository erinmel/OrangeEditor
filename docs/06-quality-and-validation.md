# Quality requirements and verification

Every number in this document is a **proposed target**, not a measured result. Baseline and release reports must retain raw samples, exact hardware/OS/driver/toolchain/dependency locks, build profile, feature flags, graph/package hashes and seed. A failed target prompts optimization or an explicit revised ADR; it cannot be relabeled a result. Isolated-plugin overhead is reported separately from native kernels. No Rust/C# speed ratio is claimed.

**Scope (ADR-22):** gates cover the M foundation rows in 01, including FR-52–55. MQTT, frequency/pitch analysis, webhooks and other deferred protocol packages have separate opt-in qualification; OBS/Twitch and browser-canvas integrations have no foundation gate. Import/export and callable-graph reuse are authoring acceptance, not merely codec tests.

## Measurement protocol and workloads

Graph tests exercise implemented behavior directly in Rust. Prefer a small set of strong behavior/property tests for foundational invariants and regressions; neither 100% coverage nor one fixture per documented case is required. G IDs are reference scenarios, not an exhaustive acceptance matrix. JSON fixtures belong at actual persisted/wire boundaries, not in a parallel test language or as a substitute for execution (ADR-20).

Reference class R: recent laptop/desktop x86-64, 8 physical cores or comparable, 16 GiB RAM, NVMe SSD, integrated GPU capable of the selected egui renderer backend, 1920×1080 at 60 Hz, no thermal throttling. macOS Apple Silicon and Linux Wayland/X11 are additional named platforms; comparisons stay within each recorded machine. Desktop target OS versions and minimum GPU requirements are frozen after P-06, not guessed from compilation alone.

Use release optimized builds without debugger, warm up 10 s, then ≥30 independent samples or ≥10,000 event latency samples. Report median/p95/p99 and max where specified; confidence intervals for throughput. Cold start clears process/cache state as documented; warm start reuses OS caches. Capture compiler time separately from execution. Disk, remote/network, decoder, vault prompt and GPU work are independently timed; loopback test results are not internet latency promises. Idle CPU is process CPU-time / wall-time expressed as percentage of one logical core. Tests with profiling/allocation instrumentation are separate from timing runs.

| Workload | Shape and purpose |
|---|---|
| W1 native dispatch | 10,000 chained checked i64 operations, nonconstant inputs; optimize-disabled graph folding versus enabled useful computation; compare direct same-kernel loop and planned native execution |
| W2 mixed pure | 10,000 math/string/list/record nodes, 1 KiB and 1 MiB payload variants; cold compile, warm reuse, branch fanout and shared immutable buffers |
| W3 expansion | Same 1/100/10,000 operation work as native, Wasm scalar, Wasm batch and worker; report transfer/guest/host scheduling separately |
| W4 editor | 10,000 nodes / 20,000 edges, ~500 visible, zoom/pan/select/drag/text; 100,000-node load as stress diagnostic, not implied interactive baseline |
| W5 async/event | 1,000 subscriptions with 100-byte events, burst 10,000 events/s then network loss; bounded queue and cancel races, repeated run restart |
| W6 files/network | 1 GiB stream through transform to temp file with 64 KiB chunks; HTTP and WebSocket loopback streams; separate disk and transport baseline |
| W7 media | 48 kHz stereo, 256-frame callback where supported; 16 prepared voices, 44.1→48 kHz conversion, selected output/cable and input capture, RMS/peak/threshold hold under declared window/hop; report capture→event latency and gaps |
| W8 lifecycle/soak | Repeated install/update/remove with active runs, malformed package/doc, vault lock, decoder failure, dropped connections and injected process termination |
| W9 graph semantics | G-suite fixtures from [11 §18](11-graph-language.md) on a virtual clock; on the W4 graph (10,000 nodes / 20,000 edges) perform 1,000 random connect/disconnect/literal/type-arg edits, and a 1,000-handler causal-chain storm with mixed reentrancy modes |

## Continuous integration quality gates

PR validation runs in stages. Stage 1 (Ubuntu) reports formatting, Clippy with warnings denied and Rust API documentation with warnings denied independently (`lint / …`, fail-fast disabled), the repository policy job (core framework guard, MSRV derivation, actionlint with shellcheck, pinned zizmor 1.30.1 workflow security audit configured by `.github/zizmor.yml`, release-helper tests) and the supply-chain job. Stage 2 starts only after lint and policy pass: `cargo test --workspace --locked`, including doctests, executes natively on Ubuntu x64, Windows x64/MSVC and macOS arm64, and `msrv` runs `cargo check --workspace --all-targets --locked` on the workspace-declared minimum compiler. Each test job writes a pass/fail/ignored table to the run summary; the `rust` job writes a per-stage results table. Dependency caches are saved only from `dev` and restored elsewhere. No Markdown or generic repository-hygiene jobs are included.

The `rust-architecture` job uses Cargo metadata to ensure known graph-core crates, including optional direct dependencies and the resolved transitive closure, remain free of UI, window, renderer and engine frameworks (Bevy, egui, eframe, epaint, winit, wgpu, Slint, iced and their subcrates). Host applications may use them. A separate release-contract job tests the release helper and validates configuration; an unconfigured release is valid configuration, not release readiness.

Pinned cargo-deny 0.20.2 is configured to check advisories, bans, licenses and sources on pull requests, pushes, manual runs and a weekly schedule. Its RustSec advisory database is refreshed online; registry or database failures fail the job. Vulnerability, unmaintained, unsound and yanked advisories are errors. Wildcard requirements fail; duplicate crate versions warn. Third-party licenses must satisfy the allowlist in `deny.toml` (Apache-2.0, MIT, Unicode-3.0, Zlib), which covers the current lockfile; adding a license is a reviewed dependency change. Unpublished workspace members are skipped, so this does not select a project license for release. Unknown registry and Git sources fail. The stable `rust` status fails if quality, metadata policy, MSRV, dependency security or any platform test fails, is cancelled or is unexpectedly skipped. These CI checks support NFR-11 and NFR-14 but do not pass their broader cross-platform, runtime or release acceptance criteria.

The pinned cargo-deny installation is cached by OS, architecture, toolchain-file hash and CLI version; hits and misses both verify its version and scan online. Advisory databases remain outside caches. Compiled jobs also use pinned Rust-cache v2.9.3 with compiler/host/environment/manifest/lock keys and separate check, MSRV, native-OS and release-target keys. Formatting has no build cache; installed binaries are excluded from Rust-cache. Incremental compilation is disabled by that action. Caches do not skip checks.

Release CD is separate from PR validation and reuses the latter with full native tests. It requires an annotated version tag, a qualified executable/license, all native packaging adapters and a commit reachable from protected main. Native release build, packaging/signing/runtime verification, digest checks and provenance precede publication of the same artifacts. The current configuration deliberately blocks CD because the application and its packaging/signing qualification do not exist. See the [release contract](../tools/release/README.md). This prepares automation without passing WU-12/G5 or claiming deployment.

### V01 test layers

ADR-20 sets the acceptance rule: each implemented semantic rule has enough meaningful evidence to distinguish correct behavior from plausible bugs. Tests live beside the code they verify.

| Layer | Tool | What to test |
|---|---|---|
| Focused component behavior | `#[test]` | Rollback, type mismatches, provider preservation |
| Named contract scenarios | `rstest` | Representative valid/invalid graphs and numeric boundaries, sharing setup |
| General invariants | `proptest` | Undo restores content; inference is deterministic; incremental validation matches full validation |
| Complete graph behavior | `rstest` | Diamonds, branches, loops and calculations through the real interpreter/runtime |

1. **Small typed graph builders.** Helpers construct graphs; assertions stay visible in each test. No custom testing language or framework.
2. **Explicit, named cases** such as `pure_cycle_rejected` and `register_feedback_allowed`. No automatic combinations unless they represent a real requirement.
3. **A pair is a starting point.** Add cases when a rule has distinct failure causes, important boundaries or interactions that one accept/reject pair cannot distinguish. Test semantic behavior rather than counting diagnostic codes.
4. **Independently expected acceptance scenarios.** Diamond: correct output, shared calculation evaluated once per epoch. Branch: only the selected effect occurs. Loop: correct final value and iteration sequence; cancellation works. Numbers: integer exactness, float precision, overflow and explicit conversion policies.
5. **Bounded generators.** Small graphs and short edit sequences first; shrinking keeps relevant structural validity; failing seeds are committed so regressions replay.
6. **Equivalence plus known answers.** Incremental/full and interpreter/executor agreement is evidence, not proof of correctness.
7. **Stable assertions.** Outputs, diagnostic codes and subject IDs, provider identities, document content and relevant execution counters. Never translated messages, incidental internal structures or large trace snapshots.
8. **JSON goldens for serialization only.** Save/load and wire compatibility; graph behavior uses Rust builders.

`rstest` is adopted incrementally, with an exact pin, when a test first removes duplicated setup with it. Existing `proptest` tests stay; already clear tests are left alone.

## CI and release evidence

Every implementation pull request, after the workspace/toolchain and CI exist: formatting/lints, applicable model/runtime unit+property+contract tests on Windows x64/Linux x64/macOS arm64; core headless build without desktop feature; document/schema/catalogue fixtures and text-reference coverage; security/redaction checks; dependency/license lock review when dependencies change. Documentation-only changes run structural/reference/contract consistency and secret checks; unexecuted or inapplicable Rust/platform tests remain labeled. [14](14-git-workflow.md) owns branch/review/merge rules, stable aggregate statuses and change-based check selection; public-contract/dependency/CI changes trigger their full affected checks. Protocol fixtures use local ephemeral containers/services or in-process equivalents; no personal credentials, live vendor accounts or physical audio in default CI. Linux broker fixtures may run centrally, while cross-OS clients still execute against explicit test endpoints in controlled CI.

Nightly: bounded fuzzing, lifecycle stress, fault injection and selected benchmarks on stable runners; full 8 h soak before release candidate, not on every tiny documentation change. Dedicated reference hardware holds performance regressions; hosted CI timing is trend evidence only. OS audio/vault/accessibility tests require signed/native builds and an explicit human verification record. Release gate cannot replace a missing hardware test with a capability table.

Evidence artifact per gate: commit/build lock, test command/tool version, status (pass/fail/unavailable/not run), related FR/NFR IDs, raw output and platform. Implementation evidence for the existing model/type/partial-validation code is recorded in 10; it does not qualify the unimplemented runtime/UI/services. New trigger, reusable-library, capture and analysis acceptance is **NOT RUN**. This scope revision verifies document consistency only. Planned commands after scaffolding: `cargo test --workspace --locked`; `cargo test -p orange-model -p orange-runtime --locked`; `cargo bench -p orange-runtime --bench execution --locked`; `cargo run -p orange-cli --locked -- run fixtures/calculation.orange --seed 1`; exact commands are finalized when crate names/features exist. Feasibility probe commands are recorded with the probes in [09](09-feasibility-probes.md).

### E2a independent pure oracle evidence

The compiled-export equivalence test is app/crates/orange-bundled/tests/reference_equivalence.rs. Its own bounded recursive demand traversal, edge scans, NodeId memoization and widened integer arithmetic are separate from compiler DFS/slots/folding and native arithmetic. Shared components are fresh semantic analysis, catalogue metadata and literal decoding, so agreement cannot independently qualify those shared components. Explicit diamond=35, first-error producer/code, signed MIN/-1 division overflow, unsigned underflow, bool Not and integer conversion boundaries guard against two implementations agreeing on a bug. The existing fresh-default/instance-override compiler test now also checks the independent oracle.

One proptest runs 128 cases per invocation over 1–24-node integer DAGs, four primitive widths, three overflow policies, all four arithmetic operations, shared dependencies, dead cones, shadowed instance literals, node UUID order unrelated to dependency order, and reversed node/edge storage. Exports preserve order and may share a producer. Each graph is checked before and after canonical JSON round trip. Values and fault origin/code are compared; reference execution counters must stay at one per demanded producer, and graph bytes/state/revision must remain unchanged. The default proptest shrinking/persistence mechanism stays enabled; this unit produced no failing seed. These are bounded regressions/properties, not exhaustive arithmetic, arbitrary-graph or full runtime qualification. Native float/conversion tests remain separate known-answer evidence; the reference oracle does not claim to cover floating semantics.
