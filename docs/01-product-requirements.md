# Product requirements

## Perspective and success

OrangeEditor is a **usable node editor foundation** (ADR-21/22): an embeddable Rust graph core, a separate reusable and extensible egui editor UI, and a basic application. People can use the application directly or build specialized products on its libraries. The foundation owns a strong node language and general capabilities; downstream products and installed plugins supply specialized workflows. Desktop and headless execution consume the same graph and package locks. The editor is a client of the runtime, not its clock.

Success means a user can configure a trigger on its node, declare/Get/Set typed variables, branch/loop over calculations, save selected logic as a callable specialized node, export/import it with dependencies, and inspect execution and failures. A third party can install a synthetic expansion while the app stays open, contribute a node, event source and editor configuration, run it, and remove it without losing the document. Downstream products use public Rust interfaces without forking the core. Speed and usability require measured evidence.

Priority: **M** required for the foundation 1.0; **S** optional/deferred, not a 1.0 gate. Phase: **P1** feasibility, **P2** language/runtime/expansion, **P3** editor and reusable graphs, **P4** triggers/files/connections, **P5** audio and qualification, **P6** optional extensions. FR IDs are stable: retired requirements retain their IDs. ADR-22 supersedes older integration and protocol release scope.

| Area | Foundation commitment |
|---|---|
| Language | Typed logic/math, strings/collections, variables declared/read/written through nodes, enum construction/matching, structured loops, branching, time, errors and cancellation |
| Authoring | Usable extensible UI, save/load/recovery, import/export, groups, typed callable reusable graphs and reusable graph templates |
| Triggers | On-node manual/test button and configurable key or combination; timers/custom events; one shared event-source contract for later plugin triggers |
| Automation | File editing/watch, HTTP/HTTPS requests and WebSocket sessions; MQTT is conditional on a bounded broker/lifecycle feasibility slice |
| Audio | Open/play/control files, select available output and input devices, basic mix/gain, RMS/peak levels and above/below-threshold events with optional hold duration |
| Conditional | MQTT, frequency-band/pitch analysis and webhook listener plugins require focused contracts/evidence before promotion; they do not block baseline |
| Specialized plugins | OBS, Twitch, website-specific APIs, TTS generation, browser-canvas/web-server integrations and scene systems are outside this delivery. Generic requests and playback of plugin-produced audio remain in scope |

**Core-first delivery sequence.** Finish validation and compilation, then deterministic headless execution for math/logic, seeded random, virtual time, loops, cancellation and resource ownership, with inert in-memory service adapters. Concrete services, package loading and UI remain later bounded slices; early evidence is collected when a public boundary needs it. This sequencing does not remove the foundation UI or services and passes no API/runtime gate by itself. [06](06-quality-and-validation.md) defines verification; the local plan orders delivery.

## Glossary

| Term | Meaning |
|---|---|
| Definition | Versioned declarative node/type description; contains no executable code |
| Implementation/provider | Executable realization of a definition or replaceable service slot |
| Package / expansion plugin | Installable OrangeEditor artifact containing definitions, executable components, assets and dependencies |
| Bundled package | Shipped package using public contracts; native kernel exception is explicitly identified |
| Snapshot | Immutable registry and provider choices pinned by a compiled execution |
| Activation | One invocation started by an entry node or event, with frame-local values; contains one or more strands |
| Run | Owned execution lifetime, variables, subscriptions, cancellation and resources; executed by one logical actor |
| Strand / segment | One control token's path through an activation / one uninterrupted execution of a strand between suspension or yield points |
| Region | Exec nodes owned by one structured construct (entry, event, Sequence step, Fork branch, loop body, function) |
| Epoch | One pull evaluation of the data inputs at a consumption site; the unit of volatile snapshot and memoization |
| Node kind | `pure`, `volatile`, `action`, `async`, `entry`, `iterator`, control/zone intrinsic, function call ([11](11-graph-language.md)) |
| Data / exec / event port | Typed value dependency / ordered control continuation / output that starts a new activation per event |
| Resource handle | Opaque capability and lifetime reference; never a serialized pointer or engine entity ID |
| Connection profile / session | Persisted configuration with secret references / live authenticated transport |
| Override slot | Named, typed and documented replacement interface with visible provider selection |
| Get/read variable | One `volatile` operation, named Get; read in each consuming epoch's prologue, never a write |
| Internationalization (i18n) / localization (l10n) | Architecture making all product text translatable / translated and reviewed resources for a particular locale; Unicode input alone provides neither |

## Workflows and boundaries

1. **Logic and reuse:** declare a typed variable → calculate/branch/loop → Get/Set → inspect → save selected logic as a callable node → export/import and obtain the same outputs with the same seed and locks.
2. **Trigger:** configure a key combination on its node, or press its test button → enqueue an activation → inspect the payload. Plugin events later use the same path; editing a binding never executes effects.
3. **Automation:** file watch or timer → bounded read → transform → HTTP request or WebSocket send → typed success/failure handling. MQTT is a conditional adapter, not an assumption that all IoT protocols ship.
4. **Audio:** select input → level remains above a threshold for a configured duration → trigger → play an opened audio file on a selected output/cable → adjust volume. A future TTS plugin supplies an audio asset or bounded PCM stream to the same playback service.
5. **Expansion and recovery:** install a synthetic plugin while open → grant authority → use its node/trigger/editor → update while a run stays pinned → remove without document loss. A failed save/install/migration recovers the last committed generation without replaying effects.

Foundation 1.0 excludes OBS/Twitch and other website-specific integrations, browser-canvas/web-server products, AMQP, GraphQL and gRPC packages, TTS generation, speech recognition, a DAW/DSP or scene editor, virtual-device/driver creation, arbitrary monkey-patching, hard real-time certification, distributed execution, collaboration and marketplace operation. Optional proposals retain their own evidence gates and do not count as foundation requirements. Generic HTTP and resource handles remain usable by later plugins.

Graph-language requirements FR-44–50 are specified normatively in [11](11-graph-language.md) and [12](12-graph-data-structures.md) and are delivered first by WU-00. FR-51 is specified in [13](13-internationalization.md), with message schemas before SDK freeze and UI qualification before authoring preview. Verification families are mapped in [06](06-quality-and-validation.md); local work-unit planning and its coverage matrix live in ignored `.artifacts/`. No M foundation requirement can be silently deferred to claim 1.0 complete; previews label their subset. FR-52–56 add authoring/service scope without changing the closed control language or passing implementation gates.

Validation evidence clarification (C4, 2026-10-23; FR-44–47): combined analysis reports the checks it actually ran and the required checks still missing. Compile readiness requires complete coverage, a pass-local valid report, and matching document-state and registry identities. Current coverage is partial (contextual contracts, regions, state and stream rules are still missing), so no graph is compile-ready; see [12 §3.2](12-graph-data-structures.md).
