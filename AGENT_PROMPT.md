# OrangeEditor architecture and planning assignment

## Outcome and boundaries
Plan OrangeEditor in an empty project directory. Deliver an implementation-ready specification for a professional, extensible node programming desktop application. Product name: OrangeEditor. Visual identity: orange accent, accessible contrast, configurable theme. Target: Windows, Linux, macOS. Language: Rust. Application/graphics framework: Bevy **0.20.0**, pinned exactly until a documented upgrade decision.

Complete planning and research before product implementation. Write Markdown, Mermaid diagrams, contract examples and schemas as documentation. Do not generate application scaffolding, Cargo manifests, production code, credentials, downloads, installations, commits, or releases in this assignment. Describe feasibility experiments and their commands; distinguish planned checks from executed evidence. Do not claim planning proves performance or reliability. Reuse no assumptions from an existing C# implementation without documenting their rationale.

Use a new architecture agent to produce the plan; the orchestrator reviews requirement coverage, version evidence, contradictions and feasibility before delivery. Bound delegated file ownership. Work autonomously on reversible decisions; record explicit assumptions and a recommended resolution for unanswered questions. Reserve user decisions for consequential product choices. Avoid generic adjectives, repeated requirements, speculative frameworks and unnecessary abstractions.

## Product objective
Users construct typed graphs to calculate values, transform strings, manipulate files, maintain state, react to events, communicate with services and control media. Graphs run interactively or headlessly. Developers and users extend the installed application through **OrangeEditor expansion plugins** installed while OrangeEditor is open. These are product packages, not Codex/MCP tools and not merely Rust crates added to a Bevy build.

Plugins can add node families, value types, codecs, connection adapters, services, editor panels, settings controls, inspectors, reusable subgraphs and future 2D/3D behavior. They can change supported base behavior through explicit extension/replacement contracts. Specify which contributions work across each plugin execution boundary. Bundled packages use the public extension contracts wherever feasible; document any privileged exception. Never silently reduce hot installation to rebuilding or restarting the application.

## Functional scope
Assign FR IDs, priority, release phase and observable acceptance criteria to each requirement.

1. Graph authoring: searchable palette, typed input/output ports, data/control/event distinctions, connection validation, configuration editors, selection, pan/zoom, groups/subgraphs, copy/paste with reference remapping, undo/redo, diagnostics, run/stop, execution inspection, save/load, recovery. Preserve editor focus and selection during unrelated edits. Plan large graph culling, hit-testing and edit-proportional updates. Include keyboard navigation, Unicode/IME, clipboard, DPI, accessibility and native dialogs in the UI feasibility decision.
2. Values: booleans, explicitly defined integer/floating types, UTF-8 strings, bytes, lists, records, JSON and schema-driven enums. Stable type and member IDs. Define null/missing/error distinctions, conversion rules, overflow/NaN behavior, numeric formatting and string indexing semantics. Custom types have versioned codecs and editor descriptions. Keep graph values separate from Bevy Entity IDs and Rust TypeId.
3. Base nodes: numeric arithmetic/comparison, math functions, logic, random with seed policy, strings/encoding/parsing/formatting, list/record/JSON operations. Math errors and loss of precision are observable; implicit conversion policy is explicit.
4. Variables: declare/define, initialize, get/read, set/update, scope, persistence and host access. Clarify redundant get/read terminology. Define write ordering, visibility, shared state concurrency, atomic operations and undo versus runtime state. Avoid making pure evaluation repeat writes.
5. Control and events: branching, enum switches, bounded/count/foreach/conditional loops, break/continue, timers, subscriptions and manual/external triggers. Define cycles, fairness, cancellation, reentrancy, event ordering, overflow/backpressure and error handling. Long loops must not freeze the UI.
6. Files: text/binary read/write, atomic replacement, append, directories/list/filter/watch, asynchronous streams, cancellation, encoding, large files, path identity/permissions and recoverable failures. Distinguish atomic visibility from crash durability. Avoid whole-file buffering as a universal design.
7. Connections: reusable versioned profiles storing endpoint, transport, authentication method, TLS policy, headers/options and credential references. Define profile scopes, import/export, validation, connection-test behavior, concurrent reuse, reconnect, shutdown and ownership. Protocol-specific settings remain typed.
8. Credentials: OS-protected credential storage on each desktop OS; secret references in graphs/profiles/packages; redacted diagnostics; vault locked/unavailable behavior; secure user input, deletion and rotation. No plaintext fallback. Distinguish application/plugin permission policy from an actual isolation boundary; native in-process code cannot be securely sandboxed by convention.
9. Protocol packages: HTTP/HTTPS, WebSockets, MQTT and AMQP. Treat user wording AMQ as an assumption requiring protocol clarification; document AMQP 0-9-1 versus 1.0 and broker compatibility. Include TLS verification, authentication, timeouts, payload limits, streaming, cancellation, retry/idempotency and protocol-specific subscription/acknowledgement/QoS semantics. Do not claim identical delivery guarantees across protocols.
10. API facilities: REST conventions and GraphQL requests/subscriptions as applicable; gRPC with HTTP/2, protobuf/descriptors, unary/client/server/bidirectional streaming; outbound webhook calls and inbound webhook listeners with authentication, binding and lifecycle. HTTP support alone does not implement gRPC or inbound webhooks. Preserve typed errors/status/metadata and cancellation.
11. Audio: select playback device per player/session, play/pause/stop/seek, volume/mixing, completion/error events, playlists, random file from folder, selection from already opened audio assets. Define decoding, supported-format research, buffering, resampling/channel mapping, concurrent playback, hotplug, device identity and fallback. Isolate real-time callbacks from allocations, locks, plugin calls and UI/network work.
12. Audio platform support: investigate application-owned virtual microphone/source registration on Linux through PipeWire and the necessary lifecycle/permissions; distinguish this from playback to a sink. Windows must select an existing virtual cable/render endpoint where present; do not assume a user-space app can create a virtual driver. Document macOS differences and external driver requirements. Provide a capability matrix with partial/unavailable behavior and hardware/manual verification.
13. Integration packages: specify bounded initial OBS and Twitch node sets, authentication/session ownership, request correlation, events, version requirements and connection/vault reuse. Demonstrate a third-party OBS extension using shared WebSocket services without duplicating their lifecycle. Treat OAuth token refresh and redaction as first-class where required.
14. Graphics expansion: define optional 2D/3D scene/resource handles and command/event bridges to Bevy. Do not require a rendered frame or window for math, files or networking. Bevy rendering availability does not imply a completed scene editor.
15. Internationalization: all product-owned UI, expansion, help, accessibility and diagnostic text must be translatable. Specify namespaced message references/catalogues, typed redacted arguments, plurals, locale selection/fallback, live language switching, RTL/font/layout checks and translation coverage. Keep user content and canonical graph values/parse/format/IDs independent of UI language. Translate presentation at the host boundary, including headless human output; preserve stable structured diagnostics. Additional shipped languages are an explicit product choice, not a reason to defer translatability.

## Architecture decisions to resolve
For each major decision record alternatives, selected approach, rationale, consequences, evidence and a falsifiable validation experiment.

- Dependency direction: graph model/type registry, compiler, execution runtime, host services, package manager/SDK, bundled packages, editor and Bevy adapter. Identify actual proposed crates and ownership; avoid premature microservices.
- Data-driven definitions versus executable implementations. Specify registry transactions, IDs/namespaces, schema/config versions, document format, codecs, migration, unresolved-node preservation and package version locking. Use compact examples of a node definition, saved graph, plugin manifest and credential-referencing connection profile. Examples must agree with the model.
- Graph compilation versus ECS scheduling. Define data dependency execution, side-effect sequencing, variable visibility and async continuations. Address function dispatch costs, caching/invalidation, allocation budgets, buffer/value ownership and zero-copy limits. Parallelize only where semantics allow it; no fabricated Rust-over-C# speedup.
- Runtime lifecycle: start, pause if supported, stop, drain, cancel, fault, restart and dispose. Define child task/session ownership, deadlines, event queue policies, generation IDs and cleanup. Blocking I/O and audio callbacks must not depend on the editor frame loop. Define the async runtime integration and bounded bridge, rather than assuming Bevy task pools satisfy every network runtime dependency.
- Plugin execution: compare native in-process, stable C ABI, WebAssembly/component interfaces and external workers against hot installation, portability, failure isolation, extension breadth, latency and UI/graphics access. Select a practical primary model and justify any additional tier. Rust ABI and raw Rust trait objects are not a stable external plugin contract. Include SDK/toolchain compatibility, packaging, discovery, local install, dependencies, integrity/origin, permissions, activation, deactivation, removal, rollback and uninstall semantics. Decide whether a registry/marketplace is later scope.
- Hot update: staging, dependency/compatibility validation, atomic registration, active graph pinning/safe points, state migration, revoked capabilities, stale handles and callbacks, in-flight I/O, unload barriers and rollback. Explicitly separate hot adding a package from replacing running code. Specify how an app remains open even when a package cannot yet unload. In-process crashes cannot be promised to be isolated by catching ordinary errors.
- Base overrides: explicit replaceable interfaces/slots, conflict resolution and user selection, immutable running registry snapshots, deterministic provider resolution, stable graph bindings, uninstall fallback and observability. No unrestricted monkey-patching. Never allow a plugin update to silently substitute an existing graph's implementation.
- UI: evaluate Bevy 0.20 UI/Feathers versus compatible integrations using exact version evidence. Choose based on editor interaction requirements, not appearance alone. Document capability gaps and experiments. Orange accent must not be the only status signal.
- Secrets/connections: threat model, service APIs, minimum plugin authority, cross-process/Wasm access, TLS defaults, OAuth lifecycle, export policies and credential-provider behavior. A process boundary alone is not an OS sandbox.

## Quality and delivery plan
Assign NFR IDs and measurable acceptance criteria for latency/throughput, runtime overhead, memory/allocation, large graph interaction, idle CPU, reliability, fault containment, security, accessibility, portability, maintainability, package compatibility, startup/shutdown and recovery. Give representative workloads, reference hardware class, build mode, sampling method, percentile, budget, verification method and release gate. All unmeasured numbers are proposed targets, not results. Separate local scheduling overhead from disk/network/codec latency. Cover cold/warm execution and pure/side-effect/async graphs.

Define unit/property/contract/integration/UI/platform/soak/fault-injection tests, protocol fixtures, hardware audio checks and CI OS matrix. Include cancellation races, package removal during execution, malformed documents/packages, secret leakage, device disappearance, unavailable vault, network loss and restart recovery. No credentials or physical devices in default CI. Keep requirements traceable to architecture, phase and acceptance evidence.

Deliver a dependency-ordered roadmap with small vertical slices, concrete outputs, acceptance tests, risks, feasibility gates and stop/go criteria. Distinguish baseline release scope from later extensions without dropping requested capabilities. Choose an early end-to-end proof of installable expansion and replacement, not a large editor shell before plugin/runtime risk is known. Define a readiness gate before product coding and separate later experiment/release gates. Do not invent calendar estimates or claim every open question blocks all progress.
