# Bevy 0.20 multi-OS pipeline research

Research date: 2026-10-20. Scope: inform CI implementation only. Sources below were retrieved from Bevy's exact `v0.20.0` release tag or Rust's official platform reference. The tag's source package manifests report `0.20.0`; GitHub's rendered tag and the exact docs.rs Rustdoc URL were inaccessible in this research session, so no mutable `main`/`latest` Bevy API evidence is used. No Bevy dependency was installed or compiled for this note.

## Workspace snapshot and decision

At requested HEAD `c6551fa`, OrangeEditor has a Rust 1.99.1 toolchain pin, workspace `rust-version = "1.97.1"`, and a tracked lockfile. `Cargo.toml` contains only `app/crates/orange-model`; Bevy is absent from both its dependency graph and `Cargo.lock`. The current `.github/workflows/checks.yml` tests the workspace on `ubuntu-24.04`, `windows-2022`, and `macos-15` (the project's current runners are Linux x64, Windows x64, macOS arm64); formatting and Clippy run on Ubuntu. The `rust` aggregate fails unless quality and the whole OS matrix succeed. This is core-only evidence today, not Bevy or desktop evidence.

Keep this matrix and the model crate Bevy-free. Do not install Bevy or add its pin to the graph-core crate. Current fail-closed checks can verify: (1) the workspace toolchain and `rust-version` stay pinned/consistent, (2) `orange-model` has no direct or transitive Bevy packages, and (3) current locked CI remains successful across the three declared OS/architectures. A repository policy check should inspect `cargo metadata --locked` package dependency closure for `orange-model`; checking that the entire lockfile contains no package named `bevy` will cease to be valid once the host harness lands. When an application crate is added, enforce its exact `bevy = "=0.20.0"` requirement and verify `cargo tree -p <host> -e features` against the committed lock; fail if a second Bevy version or unexpected default features are selected. Keep build metadata and a feature inventory as review evidence.

No Bevy-specific job belongs in the current pipeline before WU-01 creates the authorized disposable harness and resolves features. After that, add a locked Bevy compile job to the same three native OS runners and retain the core dependency-separation check. Linux job setup should install/document only the native libraries required by the selected feature graph; do not copy a blanket package list if the harness disables windowing, rendering, or audio.

## What tagged Bevy source establishes

The `v0.20.0` root manifest requires Rust 1.97.1, edition 2024, and `MIT OR Apache-2.0`. Its default features are broad (`2d`, `3d`, `ui`, `audio`). `default_platform` includes `bevy_winit`, clipboard, multi-threading, X11 and Wayland, while UI enables the built-in UI renderer and widgets. `audio` enables `bevy_audio` and Vorbis. This makes an implicit-default Bevy dependency a substantial platform commitment; WU-01 must choose and commit explicit app features before making build claims. `bevy_render` also selects a WGPU backend via its own feature/dependency graph, and compile success does not prove a physical adapter exists.

The exact-tag Linux dependency document lists Ubuntu build requirements: `g++`, `pkg-config`, `libx11-dev`, `libasound2-dev`, `libudev-dev`, and `libxkbcommon-x11-0`; it also lists `libwayland-dev` and `libxkbcommon-dev` in the context of enabling Wayland (the file's comment says “optional if you disabled the wayland feature,” which is internally confusing). GPU/driver packages such as Mesa Vulkan drivers, Intel or Radeon Vulkan packages are suggested depending on hardware. These are feature- and backend-dependent. Bevy's release `bevy_winit` manifest maps X11 and Wayland to separate upstream winit features. Treat compile-time dev packages, runtime shared libraries, a functioning compositor/session, and GPU/driver availability as distinct concerns.

Windows Rust MSVC target documentation requires host tooling; the current Rust platform reference recommends Visual Studio (2022) and the MSVC environment for `x86_64-pc-windows-msvc`. The existing `windows-2022` runner is native for that target. macOS ARM64 is a Rust Tier 1 target; the existing `macos-15` runner exercises native Apple Silicon if the runner label remains configured that way. A macOS build depends on the runner's Apple SDK/Xcode toolchain. These are host/compiler prerequisites, not proof that the packaged app launches or behaves correctly on end-user machines.

The release's `examples/app/headless.rs` explicitly shows a Bevy schedule runner without windowing/rendering and demonstrates that default features must be disabled for that profile. This supports distinct build profiles: core-only; optional headless Bevy host with only needed features; desktop Bevy host. “Headless” does not mean “renderer initialized without a display,” and neither a no-window build nor a schedule test establishes GPU/window behavior.

## Evidence levels and CI limits

- **Core correctness:** current locked workspace unit/property/contract tests on all three platforms. This proves the core compiles/runs for those targets only.
- **Bevy compile compatibility:** after WU-01, `cargo check --locked` (and selected test/build commands) for the exact Bevy and app feature graph on each native runner. It verifies Rust/native build/link prerequisites that are exercised by those features. It does not prove UI launch, compositor integration, GPU adapter selection, audio device routing, DPI, IME, clipboard, accessibility, or packaging.
- **Window/runtime smoke:** launch a minimal windowed harness in an actual desktop session on Linux Wayland and X11, Windows, and macOS. A hosted Ubuntu runner without a real interactive compositor should not be treated as this evidence. Xvfb or another virtual X server can test selected X11 window creation/event paths, but it cannot stand in for a Wayland compositor, GPU driver, desktop accessibility service, clipboard behavior, or human display interaction. Use Xvfb only for a clearly labeled, deliberately scoped smoke test. Run Wayland and X11 checks on named native Linux sessions; document unavailable sessions rather than converting them into passes.
- **GPU/rendering:** a software adapter or virtual display may help catch shader/pipeline initialization regressions, but does not establish hardware performance, hardware driver correctness, or supported minimum GPU. Record adapter/backend/driver and runner type. Reserve capability/performance and rendering qualification for named reference hardware per docs/06.
- **Audio:** Bevy's audio feature uses `rodio` playback, and the Linux dependency list includes ALSA development headers. A successful compile proves neither output-device availability nor the product's per-player endpoint routing/virtual source requirements. Those stay under B-P04 and V10 with physical/virtual devices.
- **Packaging/runtime libraries:** compile checks do not validate dynamic-library availability on clean target machines, signing/notarization, OS vault access, native dialogs, or installer behavior. WU-12/release checks need separate artifact and clean-machine evidence.

## Now vs. later recommendations

**Now (core-only pipeline):** preserve the existing three-platform locked core test matrix, strict `rust` aggregate, read-only permissions, and 1.99.1 toolchain pin. Add or retain a targeted dependency-closure tripwire that rejects Bevy anywhere below `orange-model`. Keep build claims limited to the current core and lockfile. No Linux graphics/audio system package installation is justified while the selected workspace has no Bevy dependency. Do not label this matrix as Bevy or desktop coverage.

**Later (WU-01 harness):** create the disposable harness only under the authorized WU-01 instruction; record exact Bevy package version, source/checksum, Rust toolchain, target triples, features, native package inventory and lockfile. Compare root manifest `rust-version` to release metadata and enforce exact `=0.20.0`; inspect feature unification and ensure graph crates remain Bevy-free. Build the core, headless host, and desktop host as distinct feature profiles. Run `cargo metadata --locked`, `cargo tree -e features`, and locked checks for the selected profiles. Add the exact Linux dev packages to the Linux job only when required by that graph. Exercise all three native host targets; then separately do real-window B-P06 runs on Linux Wayland/X11, Windows and macOS, recording session/runtime details. Follow B-P02 for input/accessibility/text and B-P04 for real audio endpoints. Use hardware-backed runs for GPU/performance and release evidence. WU-01 compilation is not a substitute for B-P02/B-P04/B-P06 runtime acceptance.
